# 청크 실험 기록 (2026-11-11)

## 1. 빈 페이지 (본문 50자 미만)
- 1개: 1페이지 (표지)
- 표지는 사진뿐이라 검색에서 빠지지만, 정보가 거의 없어서 영향은 적다.

## 2. 청크 크기별 비교 (overlap=50, 전체 29페이지)

| chunk_size | 청크 수 | 평균 길이 |
|-----------:|-------:|---------:|
| 300        | 65     | 225자     |
| 500        | 44     | 319자     |
| 1000       | 33     | 417자     |

## 3. 관찰
- 크기를 키울수록 청크 수는 줄고 평균 길이는 늘어난다.
- 1000으로 키워도 평균이 417자에 그친다. 카탈로그 페이지 자체가 짧아서,
  많은 페이지가 자르지 않고 통째로 1청크가 되기 때문이다 (청크는 페이지를 넘지 않음).
- 그래서 1000은 500에 비해 청크가 11개만 줄어 큰 차이가 없다.

## 4. 결정
- 일단 chunk_size=500, overlap=50으로 진행한다.
- 최종 값은 3주차 평가셋(질문 20개)의 Hit@5로 다시 비교해 정한다.

## 5. 3일차: 벡터 검색 첫 결과 (voyage-3.5, k=3, chunk 500/50)

| 질문 | 1등 페이지 | 판단 | 메모 |
|------|-----------|------|------|
| 기름 얼마나 먹어? | 27 | O | 연비 표 청크, 숫자 포함 |
| 연비가 어떻게 돼? | 27 | △ | 페이지는 맞지만 각주가 걸림 |

### 관찰
- 각주/주의 문구처럼 긴 문장이 표·목록보다 점수가 높다.
- 표가 청크로 깨져 숫자의 칸 구분이 어렵다.
- "트림"처럼 카탈로그에 없는 단어로 물으면 못 찾는다.
- → 3주차: 하이브리드 검색(BM25) + 리랭킹으로 개선 후 같은 질문으로 비교

### 관찰

- 저장소는 "어디에 두느냐"이고, 검색 품질은 "어떻게 찾느냐"가 정한다 → 3주차 하이브리드 검색에서 개선.
- 저장(scripts/ingest.py)과 사용(get_store)을 분리했다. DB에는 폴더가 없어 os.path.exists로 저장 여부를 판단할 수 없기 때문.


## 8. 2주차 수: FastAPI POST /chat

| 요청 | 기대 | 결과 |
|------|------|------|
| GET /health | 200 {"status":"ok"} | O |
| POST /chat 정상 질문 | 200 answer + sources | O |
| POST /chat 빈 질문 | 422 | O |
| POST /chat (DB 꺼짐) | 503 | O |

- pytest 3개 통과 (ask를 monkeypatch로 가짜 교체 → 외부 API 호출 0회)

### 관찰
- RAG 로직(ask)은 그대로 두고 FastAPI로 감싸기만 해서 HTTP API가 됐다. Swagger 문서는 자동 생성.
- 입력 검증(Pydantic Field)으로 빈 질문은 LLM 호출 전에 422로 막힌다 → 비용 절약.
- DB가 꺼지면 langchain_postgres가 일반 Exception으로 감싸서 던진다. 503으로 응답하고, 원인은 서버 로그(logger.exception)로 확인.
